# How it works

## Phase 0 — Application skeleton

Spring Boot starts the web server and wires the application components together.
The Maven Wrapper gives every developer the same Maven version; Java 21 is still required.
PostgreSQL runs separately in Docker and keeps its data in a named volume.
Configuration comes from application.yml, with environment variables overriding defaults.
Passwords come from the environment, while .env is ignored by Git.
The UTC Clock bean gives future services a replaceable source of Java-side time.
Actuator health reports whether the application and its database connection are healthy.
The key concept: the application is disposable; durable state belongs in PostgreSQL.

## Phase 1 — Persistence

Flyway applies V1 to create jobs and V2 to create job_runs before Hibernate starts.
Flyway records applied versions and checksums; change the schema with a new migration.
Hibernate validates the schema instead of creating or modifying it.
JSONB stores executor-specific payloads; string enums make statuses readable in SQL.
Instant maps to timestamptz, so a timestamp represents the same moment in any timezone.
The job's version column lets JPA reject an update based on an outdated copy.
Created/updated audit timestamps are generated by PostgreSQL for JPA writes.
Run history stores a job ID; PostgreSQL's foreign key removes history when the job is deleted.
The partial due index contains ACTIVE jobs; the history index supports newest-first lookups.
The key concept: migrations own the schema; JPA maps it and detects stale CRUD writes.

## Phase 2 — REST API and schedule calculations

JobController accepts validated request records; responses never expose JPA entities or lease ownership.
JobService changes database state inside transactions and flushes before returning the new version.
A PUT includes the version you read; a stale version returns 409 instead of silently losing an edit.
ScheduleCalculator uses Spring's six-field cron parser with the job's timezone and returns an Instant.
In New York, a 02:30 cron skips the spring DST gap; a 01:30 cron can occur twice during the fall overlap.
Fixed-rate schedules start one interval from the reference time; one-time schedules preserve runAt.
Pause is idempotent, resume recalculates due time, and trigger uses PostgreSQL now() to mark the job due.
The HTTP payload validator checks configuration without making requests; execution comes in Phase 3.
ProblemDetail gives clients a consistent error format, including field names for validation failures.
The key concept: an API request saves intent; a worker will later claim and execute that intent.

## Phase 3 — Claim, lease, execute, record

SchedulerLoop reserves semaphore permits before JobClaimRepository claims up to that many due rows.
FOR UPDATE SKIP LOCKED means a second worker passes over rows currently being claimed instead of waiting.
The claim transaction writes an owner and expiry, then commits; no row lock survives into execution.
That saved lease is a time-limited reservation, renewed by database-clock heartbeats while the job runs.
JobRunner creates a RUNNING row and invokes the executor with a unique run ID, attempt, and deadline.
JobExecutionRepository finishes the run and advances the job together, only if the lease is still owned and valid.
One-time success becomes COMPLETED; recurring jobs compute their next slot from completion time, with no overlap backlog.
Failures retry with capped exponential backoff and jitter; exhausted one-time jobs dead-letter, recurring jobs advance.
Claims/completions advance version; JPA updates only dirty columns, so API edits cannot restore old lease values.
The key concept: short row locks arbitrate claims; durable leases coordinate the longer execution outside transactions.

```mermaid
sequenceDiagram
    participant A as Worker A
    participant DB as PostgreSQL
    participant B as Worker B
    participant HTTP as HTTP target
    A->>DB: Claim due job J (short transaction)
    Note over DB: Lock J, set owner A + lease expiry
    B->>DB: Claim due jobs with SKIP LOCKED
    DB-->>B: Other unlocked jobs
    DB-->>A: Commit claim and release row lock
    A->>DB: Insert RUNNING run
    A->>HTTP: Execute with X-Job-* headers
    A->>DB: Heartbeat extends A's unexpired lease
    HTTP-->>A: HTTP result
    A->>DB: Complete run + advance J, WHERE owner = A
    Note over DB: Clear lease; commit outcome and next time
```

If A dies, its lease eventually expires and B can claim J again. Phase 4 adds the
janitor that labels abandoned RUNNING history rows LOST, plus the crash-recovery tests.
A crash after the HTTP effect but before completion can repeat that effect: this is
at-least-once delivery. The 500-job test demonstrates no duplicate executions during
normal concurrent operation; it does not turn delivery into a global exactly-once guarantee.

## Phase 4 — Failure and recovery

A lease is temporary ownership: heartbeats keep it alive; a dead process cannot renew it.
Claims fence abandoned runs before a replacement lease becomes visible, even on the same node.
Starting work checks the claim version, and renewal/completion check the active run as well as the owner.
The janitor locks jobs and history briefly, marks abandoned attempts LOST, and purges old terminal runs in batches.
Retries count extra attempts; delays grow exponentially with jitter, success resets retries, and poison one-time jobs dead-letter.
Timeouts interrupt cooperative executors; they cannot undo effects the target has already accepted.
SKIP ignores slots older than the agreed 60-second cutoff, while explicit retries still execute.
Shutdown stops claims before waiting; on grace expiry it cancels work and clears ownership so another worker can resume.
Polling survives database errors with backoff; if shutdown cannot reach PostgreSQL, leases expire naturally.
The key concept: recovery can repeat an external effect, so at-least-once execution still needs idempotent targets.

## Phase 5 — Observe and protect the scheduler

The API key filter checks requests before controllers and compares fixed-length hashes without logging credentials.
Role conditions create controllers for API/ALL and the engine for WORKER/ALL; worker HTTP exposes only actuator.
The SSRF guard checks every resolved IP at validation and execution, with explicit host overrides for local tests.
Redirects/proxies are disabled; Java's separate connection DNS lookup still calls for network egress controls against rebinding.
Payload/request-size bounds and nesting limits protect parsing, while DTO diagnostics redact payloads and response bodies.
Metrics count committed claims/dead letters and local attempts, and cache a database-clock view of due jobs and lag.
Logstash JSON includes scoped job/run/node MDC; execution and heartbeat threads receive context explicitly.
Readiness checks the DB and traffic state; liveness checks process state so DB outages do not cause restart storms.
The real outage check returned readiness 503/liveness 200, then recovered both readiness and polling after DB restart.
The key concept: global backlog describes shared work; local run metrics and logs explain what each pod is doing.
